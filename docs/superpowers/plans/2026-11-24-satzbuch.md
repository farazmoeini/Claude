# Satzbuch Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Offline-PWA fürs Android-Handy zum Tracken von Übungen, Fortschritt und Pausen, mit Plan-Import aus PDF.

**Architecture:** Statische Seite ohne Build-Schritt in `satzbuch/`. Reine Logik in ES-Modulen unter `satzbuch/js/` (testbar mit `node --test`), Oberfläche in `index.html` + `js/ui.js`. Daten in `localStorage`, Service Worker für offline.

**Tech Stack:** HTML/CSS/Vanilla-JS (ES-Module), pdf.js 4.x von cdnjs (als Modul, vom SW gecacht), Claude Messages API per `fetch` (optional, eigener Schlüssel), Node 22 `node:test`, Playwright zum Durchklicken.

**Spec:** `docs/superpowers/specs/2026-11-24-gym-tracker-design.md`

## Global Constraints

- Sprache der Oberfläche: Deutsch; Einheit kg; Dezimalkomma bei der Eingabe akzeptieren („72,5“).
- Standardwerte: Pause 90 s, neue Übung 3 Sätze × „10“ Wdh.
- Speicherschlüssel `satzbuch.v1`; Feld `version: 1` für spätere Migrationen.
- Keine Server, keine Konten, keine Halle41-Anbindung.
- Claude-Aufruf: Modell `claude-opus-5-5`, Header `anthropic-dangerous-direct-browser-access: true`, `output_config.format` mit JSON-Schema, Schlüssel nur in `localStorage`.
- Dunkles Design als Standard, mobil zuerst, Tipp-Flächen ≥ 44 px.

## Review Focus

1. **Laufendes Training überlebt Neuladen/Wegwischen der App:** Das aktive Training wird bei jeder Änderung gespeichert und beim Start fortgesetzt (Test in Task 2: `store` hält `aktiv`).
2. **Timer stimmt nach gesperrtem Bildschirm:** Restzeit wird aus `endetUm` berechnet, nicht runtergezählt (Test in Task 3: `restzeit(endetUm, jetzt)`).
3. **Kaputte/fremde Sicherungsdatei beim Import:** Ungültiges JSON oder falsche Struktur wirft einen Fehler und ändert nichts (Test in Task 2).
4. **Übungsnamen mit anderer Schreibweise** („Bankdrücken “ vs. „bankdrücken“) zählen als dieselbe Übung (Test in Task 3: `uebungsSchluessel`).
5. **PDF ohne Text (Scan)** ergibt eine klare Meldung statt eines leeren Plans (Test in Task 1: `parsePlanText("")` liefert `tage: []`, UI prüft das).

### Task 1: Plan-Parser

**Files:** Create `satzbuch/js/parser.js`, `satzbuch/js/util.js`; Test `satzbuch/test/parser.test.mjs`

**Interfaces – Produces:**
- `util.js`: `uid(): string`, `parseZahl(s: string): number|null` („72,5“→72.5), `normName(s): string`
- `parser.js`: `parsePlanText(text: string, name?: string): Plan` (Plan-Form wie im Spec, `quelle: "pdf"`; Übungen bekommen `pruefen: true`, wenn Sätze/Wdh. nicht erkannt), `validierePlan(obj): Plan` (wirft bei falscher Struktur, ergänzt fehlende ids/Standardwerte)

- [ ] Tests: `"Tag A – Push\nBankdrücken 3x10 80kg 90s\nSchulterdrücken 4 x 8-12"` → 1 Tag „Tag A – Push“, Bankdrücken `{saetze:3,wdh:"10",gewicht:80,pause:90}`, Schulterdrücken `{saetze:4,wdh:"8-12",pause:90}`; `"Montag\nKniebeuge 5 Sätze à 5 Wdh. 2 min Pause"` → `{saetze:5,wdh:"5",pause:120}`; `"Kreuzheben | 3 | 6 | 100 kg"` → `{saetze:3,wdh:"6",gewicht:100}`; Übungszeilen vor einer Überschrift landen in „Training 1“; `"Pause 1:30"` → 90; leerer Text → `tage: []`; `validierePlan({})` wirft.
- [ ] Tests laufen lassen → FAIL; implementieren; `node --test satzbuch/test` → PASS; commit.
